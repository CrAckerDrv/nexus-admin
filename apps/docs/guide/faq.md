# 常见问题

## 为什么不用 antd / Element Plus？

三个原因：

1. **性能**：全量引入的组件库通常 400KB+ gzip，且样式覆盖成本高
2. **可控性**：后台系统往往需要深度定制（密度、圆角、主题），自研组件只改 CSS 变量
3. **学习价值**：模板的受众是"想自己搭后台"的开发者，黑盒组件库解决不了他们对细节的掌控需求

如果团队更看重交付速度，也可以把 `packages/ui` 换成 antd——模块协议与数据层是解耦的，替换成本主要集中在页面模板。

## 为什么路由不是文件路由？

TanStack Router 支持文件路由，但本模板采用**声明式模块清单**生成路由，因为：

- 导航、路由、权限、面包屑需要来自**同一份数据**，文件路由会割裂这层关系
- 业务模块可以被整体删除/替换，不依赖文件系统约定
- 路由路径可以自由设计（如 `/business/users` 与目录结构无关）

## 深色模式下为什么没有闪白？

`index.html` 内联脚本会在 React 挂载前读取 `localStorage` 并设置 `class="dark"`。
详见 [主题与设计令牌](/guide/theming#为什么要规避闪白)。

## 虚拟滚动为什么要求固定行高？

虚拟化需要根据行高计算偏移量。如果行高不定，需要用"测量 + 回填"策略，复杂度和抖动都会显著上升。
实践中后台表格行高基本固定（40px / 46px / 54px 三档），因此固定行高是合理的取舍。

单行内容超长时请用 `truncate` 截断 + `title` 提示，而不是让行高自适应。

## 图表为什么不放进首屏？

ECharts 压缩后仍有 300KB+。模板把 `echarts/core` 放在独立 chunk，只在实际渲染图表时动态 `import()`：

```ts
const { echarts } = await import('./echart-core')
```

副作用是首次进入图表页会有一次额外请求（约 673KB / gzip 约 220KB），但换来首屏更快。

## 如何处理国际化（i18n）？

当前模板文案为中文硬编码。若要接入 i18n，推荐：

1. 用 `react-i18next`，把文案抽出到 `locales/zh-CN.json`
2. 组件的**内置文案**（如"暂无数据""加载中"）通过 `ConfigProvider` 注入
3. 日期/数字统一走 `Intl`（`formatDate` 等工具函数已使用 `zh-CN`，改为变量即可）

设置页的「界面语言」选项已预留位置。

## 为什么不使用 CSS-in-JS？

Tailwind + CSS 变量已经覆盖了后台系统的全部需求，且**零运行时**。
CSS-in-JS 的序列化开销在长列表场景会被放大（每行都要计算样式哈希），与"高性能"目标冲突。

## 构建时提示 chunk 过大怎么办？

`charts` chunk 超过 500KB 是预期内的（ECharts 本体）。可以：

- 提高 `build.chunkSizeWarningLimit`
- 或者把不常用的图表类型（如 `HeatmapChart`）从 `echart-core.ts` 中移除

`echart-core.ts` 里注册的图表/组件是精确的，删掉不需要的能立刻减小体积。
